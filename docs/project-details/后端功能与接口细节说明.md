## 工程结构

```text
Roamly
├─ ray-common   统一响应、分页、错误码、权限码和公共类型
├─ ray-pojo     DTO、VO、Entity 与业务枚举
└─ ray-server   Controller、Service、Mapper、配置、任务和基础设施适配器
```

依赖方向固定为：

```text
ray-server → ray-common + ray-pojo
```

- Controller 只暴露 DTO 和 VO，不直接返回 Entity。
- Service 负责权限后的业务规则、状态迁移和事务边界。
- Mapper 负责数据库访问、条件更新、行锁和必要的原生 SQL。
- 第三方 SDK 类型只存在于适配层，不进入公共模型或 OpenAPI。
- 业务 ID 在 Java 内部使用 `Long`，HTTP 统一使用字符串。

| 领域 | 当前方案 |

## 三个登录域

### 消费者

- 路由主要位于 `/v1/users/**` 和 `/v1/users/me/**`。
- Token 登录类型为 `CONSUMER`。
- 只能访问自己的资料、订单、券、退款、关注、消息和客服工单。
- 用户 ID 必须从认证上下文取得，不能信任请求体传入的用户 ID。

### 商户

- 路由主要位于 `/v1/merchant/**`。
- Token 登录类型为 `MERCHANT`。
- 数据范围由当前商户账号、角色和门店共同确定。
- 商户账号不能使用消费者或管理员 Token。

商户角色：

```text
VISITOR   游客，尚未完成入驻
TENANT    租户，可管理门店和员工
MANAGER   店长，可经营和管理核销
VERIFIER  核销员，只执行授权核销能力
```

商户账号状态：

```text
NOT_APPLIED
PENDING
ACTIVE
REJECTED
DISABLED
```

### 管理员

- 路由主要位于 `/v1/admin/**`。
- Token 登录类型为 `ADMIN`。
- 账号启停、首次改密和角色权限由服务端校验。
- 菜单和按钮隐藏只是体验优化，不能替代后端权限。

管理员角色：

```text
PLATFORM_ADMIN      平台超级管理员
MERCHANT_REVIEWER   商户审核员
FINANCE             财务管理员
CUSTOMER_SERVICE    平台客服
```

## 管理权限

| 权限码 | 能力 |
|---|---|
| `admin:dashboard:read` | 运营摘要 |
| `admin:user:manage` | 管理员账号治理 |
| `admin:merchant-application:review` | 商户入驻审核 |
| `admin:shop:govern` | 门店停用与恢复 |
| `admin:voucher:review` | 团购券审核 |
| `admin:trade:read` | 订单、支付和核销查询 |
| `admin:refund:manage` | 退款创建、审批、拒绝和重试 |
| `admin:commission:manage` | 服务费规则和资金账本 |
| `admin:settlement:manage` | 结算查询、重试和导出 |
| `admin:audit:read` | 操作审计查询 |
| `admin:customer-service:read` | 客服队列、详情和消息 |
| `admin:customer-service:manage` | 客服认领、回复、转交和治理 |

平台超级管理员拥有平台治理能力；其他角色只得到其业务所需权限。客服权限不能代替退款管理权限。

## 统一接口规则

### 响应

普通接口使用：

```text
Result<T>
```

分页接口使用：

```text
PageResult<T>
```

错误响应包含稳定字符串业务码、中文消息和适用的字段错误。HTTP 状态用于区分认证、权限、参数、资源不存在、冲突、限流和服务异常。

### 分页

- 普通列表从 `page=1` 开始。
- `size` 范围通常为 `1..100`。
- 客服会话等连续数据使用 ID 游标，避免翻页时重复或遗漏。
- 列表筛选在服务端完成，前端不能先分页再过滤。

### 幂等

高风险命令要求 `Idempotency-Key`，格式为 8 至 128 位字母、数字和 `._:-`。覆盖：

- 商户和团购券审核；
- 下单和 Mock 支付；
- 退款创建、审批、拒绝和重试；
- 核销和撤销；
- 服务费规则变更；
- 结算重试。

幂等由请求键、请求指纹、唯一索引和状态条件共同保证，不能只依赖 Redis 的短时缓存。

### OpenAPI

- Knife4j 入口为 `/doc.html`。
- OpenAPI 数据为 `/v3/api-docs`。
- Swagger UI 已禁用。
- prod Profile 关闭在线接口文档。
- 每个操作必须有唯一、稳定的 `operationId`。
- 业务 ID Schema 必须是字符串。

## 核心功能

### 社区和点评

- 动态统一保存在 `post`，支持普通动态和探店内容。
- 动态可关联官方内容分区、门店、图片和城市。
- 点赞、评论点赞、关注和分区关注使用独立关系表，重复操作由唯一约束处理。
- 评论支持根讨论和回复；根评论存在有效回复时，删除后保留占位。
- 每个消费者对同一门店最多一条正常点评。
- 门店评分和点评数由有效点评聚合，不信任客户端提交的计数。
- 消费认证点评要求真实核销链路。

### 地域与推荐

- 城市是候选集硬隔离条件。
- 区县只做同城软加权，不排除同城其他区县。
- 真实坐标由服务端解析城市和区县。
- 手动城市不能携带旧坐标或旧区县。
- 距离排序要求完整经纬度。
- 详细算法和测试数据见地域专题文档。

### 商户入驻与门店治理

- 游客账号可维护入驻草稿并提交审核。
- 入驻资料包含主体信息、门店分类、地址坐标、营业时间、营业执照、经营图和 Mock 结算摘要。
- 审核通过创建并激活门店，同时建立租户归属。
- 门店停用会按来源停用活动账号；恢复时只恢复因门店停用联动而停用的账号。
- 管理员不能用门店恢复覆盖员工管理或账号治理产生的停用状态。
- 私有证照和经营媒体通过鉴权下载，不暴露公共永久地址。

### 团购商品

支持四种券型：

```text
PACKAGE    套餐券
CASH       代金券
DISCOUNT   折扣券
MULTI_USE  次卡
```

商品审核状态：

```text
DRAFT
PENDING
APPROVED
REJECTED
```

销售状态：

```text
SCHEDULED
ON_SALE
OFF_SALE
SOLD_OUT
ENDED
```

- 草稿保存与提交审核分离。
- 券型创建后不能切换。
- 封面一张，详情图最多九张。
- 商品详情、标签、套餐明细和券型专属规则结构化保存。
- 审核与销售状态分离，前端不能用一个状态替代两层事实。
- 订单价格始终由服务端读取商品规则计算。

### 订单、库存和支付

订单交易状态：

```text
PENDING_PAYMENT
PAID
CANCELED
COMPLETED
```

支付状态：

```text
PENDING
SUCCEEDED
FAILED
CLOSED
PARTIALLY_REFUNDED
REFUNDED
```

- 下单按“用户 + 商品”使用 Redisson 锁减少并发竞争。
- 库存最终正确性由数据库条件更新保证。
- 待支付订单占用库存，默认 15 分钟后幂等关单并返还一次库存。
- Mock 支付成功后销量按数量累计，并按购买份数逐张发券。
- 支付回调、主动确认和任务重放不能重复发券。
- 订单交易状态和售后聚合状态分离。

### 用户券、二维码和核销

用户券状态：

```text
UNUSED
PARTIALLY_USED
USED
EXPIRED
REFUNDING
REFUNDED
```

- 每份订单商品生成一张用户券；次卡在单张券上维护总次数和剩余次数。
- 固定二维码内容为 `rq1.{tokenKey}.{signature}`。
- `tokenKey` 是随机定位值，签名绑定券、用户、版本和有效期。
- 二维码不因查看或扫码而删除。
- 核销预览不修改状态；确认核销使用预览令牌和幂等键。
- 手输券码只通过 HMAC 摘要索引定位。
- 正常撤销只允许尚未进入结算的核销，并追加反向账本。
- 核销只处理平台团购券，不记录用户到店后的线下额外消费。

### 退款、客服和结算

退款审核、渠道执行、逐券金额、服务费、资金账本、客服状态机和 T+1 结算统一见：

[退款客服与资金结算业务细节](退款客服与资金结算业务细节.md)

关键边界：

- 审核通过不等于退款成功。
- 管理端连接不等于退款处理中。
- WebSocket/SSE 只触发重新查询。
- 商户可以申请退款，不能审批退款。
- 客服可以协助处理工单，不能绕过退款权限。
- 资金金额以核销快照和追加式账本为准。

### 操作审计

- 登录、账号治理、商户审核、商品审核、退款、核销、服务费和结算敏感操作写审计。
- 审计记录操作者域、对象、动作、结果、时间和白名单摘要。
- 审计不保存密码、Token、完整手机号、证件号或完整请求体。
- 审计是追踪事实，不参与业务状态计算。

## 实时通知

### 商户 WebSocket

- 用于核销、订单和经营资源刷新。
- 连接按门店和登录身份隔离。
- 断线后页面仍可主动刷新 REST 接口。

### 管理端 SSE

- 先获取短期一次性票据，再建立 EventSource。
- 按权限接收审核、退款、核销和结算变化。
- Redis Pub/Sub 负责多实例事件分发。

### 共同边界

实时消息只包含“资源发生变化”的提示和必要资源 ID。客户端收到消息后重新请求 REST；实时连接的建立、断开和重连不得修改订单、退款、客服、核销或结算状态。

## 对象存储

- dev/test 使用本地私有存储适配器。
- prod 使用 S3 兼容存储适配器。
- 生产配置不完整时启动失败，不静默回退到本地目录。
- 业务媒体与客服附件都保存对象键，不把本地绝对路径作为公开接口。
- 私有文件每次读取都重新校验身份、业务归属和可见性。
- 临时文件过期后由后台任务清理。

## 后台任务

| 任务 | 默认调度 | 作用 |
|---|---|---|
| 待支付关单 | 每 30 秒扫描 | 关闭超时订单并返库存 |
| 券过期 | 周期扫描 | 推进符合条件的用户券状态 |
| 商品上下架 | 周期扫描 | 根据销售时间刷新状态 |
| 临时媒体清理 | 周期扫描 | 删除过期未绑定对象 |
| 退款执行 | 每 5 秒扫描 | 租约领取 Mock 退款任务 |
| 自动过期退款 | 每天 00:10 | 为符合规则的券创建退款 |
| T+1 结算 | 每天 02:00 | 汇总前一日可结算账本 |
| 客服 SLA | 每 60 秒 | 标记超时工单 |
| 客服自动关闭 | 每小时 | 关闭空闲 7 天的等待/已解决工单 |

任务服务必须幂等并允许重复调度。Spring Scheduling 可在生产规模扩大后替换为独立任务平台，但数据库状态和唯一约束仍是最终事实。

## 配置与环境

```text
.env                    本地真实变量，不提交
.env.example            脱敏变量模板
application.yml         公共结构和环境变量占位符
application-dev.yml     开发差异
application-test.yml    测试差异
application-prod.yml    生产差异
```

- 默认 Profile 为 dev。
- dev 可执行含 `DROP TABLE` 的完整初始化，只能连接明确允许重建的隔离数据库。
- 连接需要保留数据的数据库时必须设置 `SPRING_SQL_INIT_MODE=never`。
- 生产关闭开发初始化、Knife4j 和 OpenAPI 数据端点。
- JWT、数据库、Redis、S3 和外部渠道密钥只能通过环境注入。
- `.env` 不得进入 Git。

## 数据库规则

- 当前是 51 张业务表的完整 Demo 快照。
- 不使用 Flyway 或 Liquibase。
- `schema-init.sql` 是结构真源，`seed-dev.sql` 是开发样例真源。
- 不声明物理外键，逻辑关联由 Service 事务、唯一约束和权限校验维护。
- 金额统一保存为分，费率保存为基点。
- 新环境可以执行完整快照；已有数据环境不能直接运行含 `DROP TABLE` 的脚本。
- 详细表目录、索引、关系和种子账号见数据库专题文档。

## 安全边界

- 密码使用 BCrypt。
- 三个登录域的 Token 不能互换。
- 登录失败、限流和账号停用均由服务端处理。
- 用户联系方式、证照、结算资料和私有媒体按角色投影与脱敏。
- 日志禁止记录密码、JWT、短信验证码、密钥和完整敏感字段。
- 券码和二维码使用摘要或签名定位，不公开裸数据库 ID。
- 跨用户、跨商户和跨工单资源统一返回不泄露存在性的错误。
- 管理敏感操作同时要求权限、状态校验和审计。

## 本地运行

1. 安装 Java 21、Maven 3.9+、MySQL 8.x 和 Redis 6.0+。
2. 复制 `.env.example` 为 `.env` 并填写开发依赖。
3. 用 IDEA 导入根 `pom.xml`。
4. Project SDK 选择 Java 21。
5. 运行 `ray-server` 的 `com.ray.RayRoamlyApplication`。
6. Working directory 使用后端仓库根目录。

开发入口：

```text
应用       http://localhost:8081
Knife4j   http://localhost:8081/doc.html
OpenAPI   http://localhost:8081/v3/api-docs
```

生产 Nginx 对外提供 `/api` 前缀，并在转发时剥离此前缀。客户端基地址配置为 `https://example.com/api`，业务路径仍写 `/v1/**`。

## 验证

常用命令：

```text
mvn test
mvn -DskipTests compile
mvn -pl ray-server -am dependency:tree
```

涉及真实数据库的测试必须显式开启相应环境开关，并且只连接允许重建的隔离开发库。默认测试中的条件跳过不等于对应生产基础设施已经验证。

## 当前限制

- 支付、退款和结算为 Mock，不可用于真实资金处理。
- 没有完整生产清分清算、渠道日终对账和会计总账。
- 没有动态 RBAC、组织部门、多租户数据源或通用工作流引擎。
- 没有完整客服机器人、全渠道接入或外部客服平台适配器。
- 后台任务使用应用内 Spring Scheduling，生产多实例容量需要继续评估。
- 初始化 SQL 是可重建 Demo 快照，不是保留数据环境的迁移方案。
