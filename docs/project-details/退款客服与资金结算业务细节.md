# Roamly 退款、客服、服务费与资金结算业务细节

> 文档状态：当前实现说明（Mock 资金链路）  
> 更新时间：2026-09-13  
> 适用范围：团购订单、用户券、核销、退款审核与执行、资金账本、今日收银、收入明细、T+1 结算、平台客服  
> 结构真源：`ray-server/src/main/resources/schema-init.sql`  
> 接口真源：运行时 `/v3/api-docs`

## 1. 文档目的

本文把退款、客服、服务费、核销收入和结算放在同一条业务链路中说明，解决以下容易混淆的问题：

- 退款“待审核”“等待执行”“处理中”“失败”“人工处理”分别由什么动作触发；
- 审核为什么不能等同于退款执行；
- 管理端连接、WebSocket 连接和客服在线为什么不能修改退款状态；
- 未核销退款与已核销退款为什么会产生不同的账本分录；
- 服务费按什么基数计算，规则变化后历史数据是否变化；
- 今日收银、核销明细、收入明细和结算为什么必须使用同一份核销快照；
- 已经结算的核销发生退款后，资金如何进入后续结算周期；
- 客服工单如何认领、回复、转交、关闭，以及客服为什么不能绕过退款权限直接退款。

本文描述的是 **2026-09-13 仓库源码中的实际实现**。规划中的能力会明确标记为“尚未实现”，不会因为表中预留了字段或阶段文档曾提出目标就写成已经完成。

## 2. 一页总览

### 2.1 完整业务链路

```text
消费者下单并完成 Mock 支付
  → 支付金额冻结，按购买份数发放用户券
  → 商户核销某张券
  → 保存不可变的核销金额与费率快照
  → 账本确认商家毛应收并扣除服务费
  → T+1 按门店汇总结算账本

任何阶段发起退款
  → 校验订单、券、申请人和重复申请
  → 自动审核或等待人工审核
  → 审核通过后创建退款执行尝试
  → 退款 Worker 原子领取任务
  → 调用 Mock RefundGateway
  → 成功：更新券、退款、支付、售后和账本
  → 失败：等待重试或转人工处理

发生业务争议
  → 消费者或商户创建平台客服工单
  → 平台客服认领、回复、备注、转交和解决
  → 客服可查看经过权限校验的订单/券/核销/退款上下文
  → 退款审批和执行仍走独立退款权限与状态机
```

### 2.2 四类权威事实

| 事实 | 权威来源 | 不能替代它的内容 |
|---|---|---|
| 订单是否已支付 | 订单交易状态和支付记录 | 退款状态、客服状态 |
| 退款走到哪一步 | 退款审核状态、执行状态、逐券明细、执行尝试 | 订单旧退款状态、管理端是否在线 |
| 商家应收多少 | 核销金额快照和资金账本 | 商品当前价格、页面临时计算 |
| 客服工单由谁处理 | 工单状态和 `assignee_admin_id` | WebSocket 是否连接、页面是否打开 |

## 3. 全局数据口径

### 3.1 金额、费率和币种

- 所有数据库金额均为整数“分”，例如 `1990` 表示人民币 `19.90` 元。
- 所有费率均为基点 `bps`，`10000 bps = 100%`，`500 bps = 5.00%`。
- 服务端业务计算使用整数金额或 `BigDecimal`，禁止使用 `float/double`。
- 当前币种固定按人民币解释，核销表尚未保存独立的币种字段；接入多币种前必须补充币种快照，不能只依赖系统默认值。
- 对外展示时由前端把分格式化为元；前端不能反向计算并覆盖后端金额。

### 3.2 ID 口径

- 数据库与 Java 服务内部业务 ID 使用 `BIGINT/Long`。
- HTTP 和 OpenAPI 中的业务 ID 统一使用字符串。
- 前端不得把雪花 ID 转为 JavaScript `Number`，否则可能丢失精度。

### 3.3 时间口径

- 今日收银按 `Asia/Shanghai` 自然日统计。
- 自动过期退款按北京时间每天 `00:10` 扫描。
- 默认 T+1 结算按北京时间每天 `02:00` 生成。
- 后台任务必须按数据库事实幂等恢复，不能依赖某个页面或 WebSocket 长期在线。

### 3.4 数据库管理口径

- 当前结构基线为 51 张业务表。
- 不使用 Flyway。
- 新环境用 `schema-init.sql` 初始化。
- 已有开发数据库只手工执行经过审查的 SQL 修改段，应用启动不自动改表。
- 相关表不使用物理外键；关联完整性由服务层事务、权限校验、行锁和唯一索引维护。

## 4. 必须分开的状态

### 4.1 订单交易状态

```text
PENDING_PAYMENT  待支付
PAID             已支付
CANCELED         已取消
COMPLETED        已完成
```

新退款流程不会把订单交易状态改成 `REFUNDING` 或 `REFUNDED`。这两个旧订单状态仅用于兼容历史读取。订单已经支付与订单正在售后并不矛盾，因此订单可以保持 `PAID`，同时 `after_sale_status` 显示退款进度。

### 4.2 订单售后状态

```text
NONE
APPLYING
UNDER_REVIEW
APPROVED
REJECTED
REFUNDING
PARTIALLY_REFUNDED
REFUNDED
REFUND_FAILED
CLOSED
```

售后状态用于列表聚合和用户理解，不代替退款主记录、逐券明细和执行尝试。

### 4.3 退款聚合状态

```text
REQUESTED   已提交申请
PROCESSING  审核通过并进入执行流程
SUCCEEDED   本申请退款成功
FAILED      本申请执行失败
REJECTED    审核拒绝
```

### 4.4 退款审核状态

```text
PENDING_REVIEW   等待人工审核
AUTO_APPROVED    规则自动通过
MANUAL_APPROVED  管理员人工通过
REJECTED         管理员拒绝
```

审核只回答“是否允许退”，不回答“渠道是否已经把钱退成功”。

### 4.5 退款执行状态

```text
WAITING_EXECUTION  等待 Worker 执行
PROCESSING         某个 Worker 已取得有效租约并正在执行
SUCCESS            全部目标明细成功
PARTIAL_SUCCESS    部分目标明细成功
FAILED             本轮执行失败
RETRY_WAITING      等待下一次重试
MANUAL_REQUIRED    自动重试耗尽，需要人工处置
```

兼容值：

- `NOT_STARTED`：审核拒绝或尚未启动执行的兼容表达；
- `SUCCEEDED`：部分旧数据和查询仍兼容此成功值；当前 Worker 成功写入 `SUCCESS`。

`PARTIAL_SUCCESS` 和 `FAILED` 已进入枚举与查询契约，但当前单次 Mock Worker 对一个退款申请执行整单成功或整单重试，正常执行路径不会生成逐明细一部分成功、一部分失败的 `PARTIAL_SUCCESS`。当前页面常见的“部分退款”主要指多券订单只选择部分券发起并成功，订单售后聚合为 `PARTIALLY_REFUNDED`。

### 4.6 客服工单状态

```text
OPEN              待认领
CLAIMED           已认领/处理中
WAITING_CUSTOMER  等待消费者回复
WAITING_MERCHANT  等待商户回复
WAITING_INTERNAL  等待平台内部协作
RESOLVED          已解决，可重新打开
CLOSED            已关闭，普通接口不可继续修改
```

### 4.7 WebSocket 的边界

WebSocket/SSE 只负责通知客户端“数据可能变化，请重新查询权威接口”。以下动作均不得修改业务状态：

- 管理端打开或关闭页面；
- 客服上线或离线；
- WebSocket 建连、断线或重连；
- 浏览器刷新；
- 消费者或商户进入详情页。

因此，“没有 WebSocket 就待处理，一连接就处理中”只适合描述连接状态，不适合退款和客服业务状态。退款 `PROCESSING` 必须由 Worker 成功领取执行任务触发；客服 `CLAIMED` 必须由认领操作触发。

## 5. 服务费规则

### 5.1 当前公式

```text
商家毛应收 = 顾客实付 + 平台补贴
服务费基数 = max(0, 商品售价 - 商家补贴)
服务费 = 服务费基数 × 服务费率
商家预计收入 = 商家毛应收 - 服务费
```

字段 `platform_discount_amount` 虽然名称是“平台优惠金额”，当前资金语义等同于“平台补贴”。文档和页面可显示为平台补贴，但数据库字段暂时保持兼容。

### 5.2 费率优先级

核销发生时按以下顺序确定费率：

1. 查询该门店在核销时间点生效的服务费规则；
2. 没有门店规则时使用平台默认规则；
3. 仍没有规则时使用系统默认 `500 bps`，即 `5.00%`。

规则按核销发生时间取值并保存快照。以后修改费率不会重算历史核销。

### 5.3 舍入口径

当前金额单位已经是分，实现等价于：

```text
服务费（分） = 服务费基数（分） × rate_bps / 10000
```

整数除法不足 1 分的部分截断，不产生小数分。对账和测试必须复用同一算法，不能在前端按浮点数四舍五入得到另一个结果。

### 5.4 异常基数

当 `商品售价 - 商家补贴 < 0` 时，服务费基数按 0 处理。该情况意味着补贴配置异常，业务上应记录日志并排查配置，但不得计算负服务费。

### 5.5 示例

假设：

```text
商品售价      10000 分（100.00 元）
商家补贴       1000 分（10.00 元）
平台补贴        500 分（5.00 元）
顾客实付       9000 分（90.00 元）
服务费率        500 bps（5.00%）
```

则：

```text
服务费基数 = 10000 - 1000 = 9000 分
服务费     = 9000 × 500 / 10000 = 450 分
商家毛应收 = 9000 + 500 = 9500 分
预计收入   = 9500 - 450 = 9050 分
```

## 6. 核销快照与多份分摊

### 6.1 为什么必须保存快照

核销后商品可能改价、补贴规则可能调整、服务费率也可能变化。如果结算或退款时重新读取商品当前值，历史金额会漂移。因此每次核销必须保存当时的金额事实：

- 商品售价；
- 商家补贴；
- 平台补贴；
- 顾客实付；
- 服务费基数；
- 服务费率；
- 服务费；
- 商家预计收入；
- 对应核销时间。

当前 `voucher_redemption` 已保存对应的 `sale_amount`、`merchant_subsidy_amount`、`platform_discount_amount`、`customer_paid_amount`、`service_fee_base_amount`、`service_fee_rate_bps`、`service_fee_amount` 和 `estimated_income_amount`。

当前核销表尚无独立 `currency` 和 `calculation_version` 字段，人民币和现有算法版本由系统约定隐式表达。这是未来多币种或多版本并行计算前需要补齐的结构能力。

### 6.2 次卡和多份券分摊

一笔订单包含多份券时，支付金额、补贴和服务费需要分配到每张券。当前规则是：

1. 先按份数整数均分；
2. 除不尽的余数放在最后一份或最后一次；
3. 所有逐券金额相加必须严格等于订单总金额。

例如 `1000 分 ÷ 3`，三份应为 `333、333、334`，不能三份都记 `333` 后丢失 1 分。

### 6.3 核销账本

核销成功写入两类主要分录：

| 分录类型 | 方向 | 金额 | 含义 |
|---|---:|---:|---|
| `REDEMPTION_RECOGNIZED` | CREDIT | 顾客实付 + 平台补贴 | 确认商家毛应收 |
| `SERVICE_FEE_RECOGNIZED` | DEBIT | 服务费 | 扣除平台软件服务费 |

同一核销事件使用：

```text
business_event_id = REDEMPTION-{redemptionId}
```

数据库通过 `business_event_id + entry_type + account_side` 唯一约束防止同一业务事件重复入账。

### 6.4 撤销核销

正常撤销仅允许用于尚未进入结算的核销，判断依据是 `settlement_item` 是否已经包含 `REDEMPTION-{redemptionId}` 事件。

撤销时写入：

- `REDEMPTION_REVERSED`：负向冲回核销收入；
- `SERVICE_FEE_REVERSED`：正向返还原服务费。

已进入结算的历史事实不应被直接改写；后续退款通过新的负向账本进入下一结算周期。

## 7. 资金账本原则

### 7.1 账本是追加事实

资金账本采用追加分录，不通过修改历史金额来表达冲回。这样可以回答：

- 原始核销确认了多少；
- 哪次退款冲回了多少；
- 服务费返还了多少；
- 哪些分录进入了哪个结算批次；
- 同一事件是否被重复记账。

### 7.2 主要分录

| 业务动作 | 分录 | 是否进入商家结算 | 说明 |
|---|---|---|---|
| 支付成功 | `PAYMENT_FROZEN` | 否 | 平台支付冻结事实 |
| 核销成功 | `REDEMPTION_RECOGNIZED` | 是 | 商家毛应收 |
| 核销成功 | `SERVICE_FEE_RECOGNIZED` | 是 | 服务费扣减 |
| 核销撤销 | `REDEMPTION_REVERSED` | 是 | 毛应收负向冲回 |
| 核销撤销 | `SERVICE_FEE_REVERSED` | 是 | 服务费正向返还 |
| 消费者退款成功 | `REFUND_REVERSED` | 否 | 冲回支付冻结金额 |
| 已核销退款成功 | `REFUND_REVENUE_REVERSED` | 是 | 冲回商家核销收入 |
| 已核销退款成功 | `SERVICE_FEE_REFUNDED` | 是 | 返还原服务费 |
| 人工账务调整 | `SETTLEMENT_ADJUSTMENT` | 是 | 按分录正负进入结算 |

旧 `COMMISSION_RECOGNIZED/COMMISSION_REVERSED` 仍作为兼容类型纳入结算，新流程使用服务费命名。

## 8. 退款资格与申请

### 8.1 三类人工来源和系统来源

```text
CONSUMER  消费者申请
MERCHANT  商户申请
ADMIN     管理员申请
SYSTEM    系统自动过期退款
```

来源决定身份校验和审核策略，但不能改变资金计算规则。

### 8.2 基础资格

创建退款申请前至少检查：

- 订单必须为 `PAID`；
- 目标券必须属于同一订单；
- 申请人必须有权访问订单和券；
- 券不能已经退款；
- 同一张券不能存在其他活动退款；
- 商品及退款规则必须存在；
- 退款金额不能超过该券可退金额；
- 多券申请的每张券都要逐张校验，不能只校验订单第一张券。

### 8.3 未核销和已核销权限差异

- 消费者只能申请 `UNUSED` 券退款。
- 商户或管理员可以对 `USED` 券发起退款，但必须进入人工审核。
- 未过期券是否可退由 `refundAnytime` 规则决定。
- 已过期券是否可退由 `refundExpired` 规则决定。
- 自动过期扫描覆盖 `UNUSED` 和 `EXPIRED`，执行前仍会复核券状态和重复申请。

### 8.4 自动过期退款

- 默认每天北京时间 `00:10` 扫描；
- 每批最多处理 200 张券；
- 幂等键为 `AUTO-EXPIRED:{voucherId}`；
- 执行前重新检查是否已退款、已核销、已有活动申请或已进入人工处理；
- 定时扫描只创建符合规则的退款事实，不能凭“到时间”绕过资格校验。

### 8.5 逐券退款金额

消费者实际退款金额来源于订单实付金额的逐券分摊：

```text
逐券顾客实付 = 订单 payAmount 按 quantity 均分，余数归最后一张
```

创建退款明细时优先使用 `user_voucher.customer_paid_amount` 作为 `refundable_amount`。平台补贴不是退给消费者的钱；它在已核销退款时作为商家收入冲回的一部分处理。

### 8.6 锁券

退款申请创建成功后，目标券从 `UNUSED` 或 `USED` 进入 `REFUNDING`。锁券的目的包括：

- 阻止退款期间继续核销；
- 阻止同一张券重复申请退款；
- 让消费者和商户看到售后处理中事实。

审核拒绝后，已核销券恢复为 `USED`，未核销券恢复为 `UNUSED`。

## 9. 退款审核

### 9.1 审核的职责

审核负责回答：

- 申请人和业务归属是否合法；
- 商品退款规则是否允许；
- 已核销退款是否有足够依据；
- 是否允许进入渠道执行；
- 拒绝时给出什么理由、由谁作出决定。

审核不负责：

- 直接把钱退回；
- 模拟渠道成功；
- 写入成功退款账本；
- 因管理端在线而把状态改成处理中。

### 9.2 自动审核

符合自动退款条件的未核销券可写入 `AUTO_APPROVED`，随后创建执行尝试并进入 `WAITING_EXECUTION`。

### 9.3 人工审核

需要人工判断的申请保持 `PENDING_REVIEW` 和售后 `UNDER_REVIEW`。管理员通过后写入：

- 审核状态 `MANUAL_APPROVED`；
- 审核人和审核时间；
- 退款聚合状态 `PROCESSING`；
- 执行状态 `WAITING_EXECUTION`；
- 一条可领取的执行尝试。

### 9.4 拒绝

拒绝后：

- 审核状态变为 `REJECTED`；
- 退款聚合状态变为 `REJECTED`；
- 执行状态使用 `NOT_STARTED`；
- 保存拒绝人和拒绝原因；
- 已核销券恢复 `USED`，未核销券恢复 `UNUSED`；
- 逐券退款明细变为失败/终止状态；
- 不调用退款网关；
- 不写成功退款账本；
- 订单售后根据其余券的真实状态重新聚合。

## 10. 退款执行、租约与恢复

### 10.1 执行链路

```text
RefundExecutionCoordinator 每 5 秒扫描
  → 每批查找最多 20 条可运行尝试
  → RefundExecutionLeaseService 用条件更新领取
  → 领取成功：status=PROCESSING、写 lease_owner/lease_until、retry_count+1
  → 提交短事务
  → RefundExecutionWorker 在事务外调用 RefundGateway
  → RefundExecutionResultService 开新事务锁定尝试
  → 校验 lease_owner
  → 写渠道结果、退款聚合、逐券、支付、售后和账本
```

### 10.2 为什么渠道调用不能放在领取事务中

渠道调用可能超时或延迟。如果在持有数据库事务和行锁时调用渠道，会造成：

- 长事务；
- 锁等待扩大；
- 数据库连接被长时间占用；
- 失败恢复困难。

当前实现把领取、渠道调用和结果提交拆开，渠道调用发生在数据库事务外。

### 10.3 原子领取条件

可领取任务包括：

- `WAITING` 或 `RETRY_WAITING`，且 `next_retry_at` 已到；
- `PROCESSING` 但租约已经过期。

领取使用单条带状态和租约条件的 `UPDATE`。只有返回影响行数为 1 的实例取得执行权，因此两个实例扫描到同一 ID 时也只能有一个执行。

### 10.4 租约

- 当前租约为 30 秒；
- `lease_owner` 标识本次执行实例；
- 结果提交前重新锁定尝试并校验租约所有者；
- Worker 崩溃或本地结果提交失败后，租约到期可被其他实例重新领取；
- 重放仍使用同一渠道幂等键，避免渠道侧重复退款。

### 10.5 Mock 网关场景

| 场景 | 第一次调用 | 后续调用 | 最终行为 |
|---|---|---|---|
| `SUCCESS` | 成功 | 成功 | 立即完成 |
| `FAIL_ONCE` | 失败 | 第二次成功 | 可验证真实重试 |
| `ALWAYS_FAIL` | 失败 | 持续失败 | 默认第三次进入人工处理 |
| `DELAYED` | 处理中 | 第二次成功 | 可验证异步结果语义 |

普通失败或处理中后，`next_retry_at` 默认设置为当前时间加 10 秒。重试必须再次调用 Mock 网关，不能只修改数据库状态。

### 10.6 渠道成功、本地提交失败

该故障窗口的恢复方式是：

1. 渠道通过幂等键识别同一退款请求；
2. 本地租约到期后任务可被重新领取；
3. Worker 用同一幂等键重放；
4. 渠道返回同一成功事实；
5. 本地结果事务再次写入；
6. 账本唯一约束防止重复入账。

## 11. 退款成功后的逐项处理

### 11.1 所有成功退款

- 券从 `REFUNDING` 变为 `REFUNDED`；
- 逐券明细写 `SUCCESS`；
- `refund_amount = refundable_amount`；
- 写 `REFUND_REVERSED`，金额为消费者实际退款金额的负数；
- 退款主记录聚合为 `SUCCEEDED/SUCCESS`；
- 支付状态按订单全部券是否退款聚合为 `PARTIALLY_REFUNDED` 或 `REFUNDED`；
- 订单交易状态仍保持 `PAID`；
- 订单售后状态按券聚合为 `PARTIALLY_REFUNDED` 或 `REFUNDED`。

### 11.2 未核销券退款

未核销券尚未确认商家核销收入，也未扣服务费，因此：

- 退给消费者：逐券顾客实付；
- 写 `REFUND_REVERSED` 冲回支付冻结；
- 不写 `REFUND_REVENUE_REVERSED`；
- 不写 `SERVICE_FEE_REFUNDED`；
- 不冲回不存在的商家核销收入；
- 不返还未曾收取的服务费。

### 11.3 已核销券退款

已核销券已经产生商家收入和服务费，因此除消费者退款外还要写：

```text
核销收入冲回 = -(顾客实付 + 平台补贴)
服务费返还   = +原核销服务费
```

对应分录：

- `REFUND_REVERSED`：冲回消费者支付冻结金额；
- `REFUND_REVENUE_REVERSED`：冲回商家毛应收；
- `SERVICE_FEE_REFUNDED`：把原服务费返还给商家。

逐券退款明细保存 `reversed_income_amount` 和 `refunded_service_fee_amount`，便于时间线、结算和对账追溯。当前 `reversed_income_amount` 保存的是原商家预计收入净额；实际账本则拆成“商家毛应收负向冲回”和“服务费正向返还”两条分录，两者净影响等于该字段，不能把该字段再与服务费返还重复相加。

### 11.4 部分退款

多券订单按券退款。只更新本次申请包含的券，其余券继续保持原状态和可用性。

例如订单有 3 张券，仅退第 2 张：

- 第 2 张变为 `REFUNDED`；
- 第 1、3 张仍可按各自状态使用；
- 支付状态变为 `PARTIALLY_REFUNDED`；
- 售后状态变为 `PARTIALLY_REFUNDED`；
- 账本只记录第 2 张券对应金额；
- 后续可对第 1、3 张分别申请，但同一张券不能再次退款。

### 11.5 执行失败和人工处理

- 可重试失败进入 `RETRY_WAITING`；
- 到达 `next_retry_at` 后重新领取并再次调用网关；
- 自动重试耗尽后进入 `MANUAL_REQUIRED`；
- 售后状态进入 `REFUND_FAILED`；
- 此时不能伪造成功退款账本；
- 管理端“重试”必须创建或恢复真实执行尝试，而不是直接把主状态改成成功。

## 12. 退款时间线与三端展示

### 12.1 推荐展示顺序

```text
申请已提交
→ 自动审核通过 / 等待人工审核
→ 管理员通过或拒绝
→ 等待退款执行
→ 渠道处理中
→ 执行失败并等待重试（可多次）
→ 退款成功 / 需要人工处理
```

### 12.2 管理端队列含义

| 页面队列 | 主要判断依据 |
|---|---|
| 待审核 | `review_status=PENDING_REVIEW` |
| 等待退款 | 审核已通过且 `execution_status=WAITING_EXECUTION` |
| 处理中 | `execution_status=PROCESSING` |
| 退款失败 | `FAILED` 或 `RETRY_WAITING` |
| 人工处理 | `MANUAL_REQUIRED` |
| 已完成 | `SUCCESS` 或兼容成功值 |
| 部分退款 | 当前主要按订单售后 `PARTIALLY_REFUNDED` 聚合；`PARTIAL_SUCCESS` 为执行契约预留 |
| 已拒绝 | `review_status=REJECTED` |

“处理中”没有“通过”按钮是合理的：通过/拒绝属于审核阶段；处理中表示审核已经结束，Worker 正在调用退款渠道。此时应展示执行尝试、失败原因和必要时的重试/人工处理入口。

### 12.3 消费者和商户端

- 消费者看审核意见、实际退款金额、执行状态、失败原因和时间线；
- 商户可以申请、查看审核和 Mock 执行结果，但不能审批或执行退款；
- 两端都不能只根据订单 `status` 推导退款中或已退款；
- 页面收到实时事件后重新查询退款详情，不自行推进状态。

## 13. T+1 结算

### 13.1 结算周期

默认每天北京时间 `02:00` 为结算日期 `D` 生成批次，收集：

```text
[D-1 00:00:00, D 00:00:00)
```

区间内尚未被结算的可结算账本分录按 `shop_id` 分组。每个门店每个结算日期只允许一个批次，唯一键为：

```text
(shop_id, settlement_date)
```

### 13.2 纳入结算的分录

```text
REDEMPTION_RECOGNIZED
SERVICE_FEE_RECOGNIZED
COMMISSION_RECOGNIZED        旧兼容
REDEMPTION_REVERSED
SERVICE_FEE_REVERSED
COMMISSION_REVERSED          旧兼容
REFUND_REVENUE_REVERSED
SERVICE_FEE_REFUNDED
SETTLEMENT_ADJUSTMENT
```

不直接纳入：

```text
PAYMENT_FROZEN
REFUND_REVERSED
```

原因是商家结算围绕“已确认的核销收入及其冲回”计算，而不是围绕消费者支付冻结和支付退款流水直接计算。

### 13.3 结算金额方向

```text
核销收入确认             正数
服务费确认               负数
核销撤销/退款收入冲回    负数
服务费撤销/退款返还      正数
人工调整                 按账本原符号
```

批次金额：

```text
settlement_batch.total_amount
= 该批次所有 settlement_item 对应账本金额之和
```

### 13.4 批次生成过程

```text
查询结算窗口内未结算账本
→ 按门店分组
→ 创建 PROCESSING 结算批次
→ 创建 settlement_item 逐条关联账本
→ 创建首次 settlement_attempt
→ 调用当前 Mock 结算逻辑
→ 成功后批次变为 SUCCEEDED
```

### 13.5 已结算后退款

已经成功的历史批次不重写。若某张已结算券在之后退款：

1. 退款成功日写入新的 `REFUND_REVENUE_REVERSED`；
2. 同时写入新的 `SERVICE_FEE_REFUNDED`；
3. 两条新分录在下一次结算窗口被收集；
4. 后续批次以净负向调整减少门店应结金额；
5. 历史批次仍保留当时真实结算结果。

若后续批次合计为负数，真实生产系统还需要定义“抵扣后续收入、生成商户应收款或人工追缴”的策略；当前 Demo 不等同于完整生产清分清算系统。

### 13.6 管理端重试

- 重试要求 `Idempotency-Key`；
- 已成功批次禁止重试；
- 相同 key 重放已有结果；
- 新 key 创建新的 `settlement_attempt`；
- 当前 Mock 场景固定为 `SUCCESS`。

### 13.7 当前结算实现的明确限制

退款执行已经有 Coordinator、租约和 Worker，结算目前没有达到同样的异步任务化程度：

- 当前结算 Mock 在事务内同步执行；
- `settlement_attempt` 虽预留租约、重试和失败字段，但尚未实现独立的异步结算 Worker；
- 尚未实现真实银行/微信商户转账、渠道回调、日终对账文件和差错处理；
- 尚未实现负结算余额的完整追缴模型；
- 尚未实现生产级清分、清算、打款和会计总账。

因此不能把“表里有租约字段”理解为“结算已具备退款同等级别的原子领取和失败恢复”。

## 14. 今日收银、团购数据、核销明细和收入明细

### 14.1 页面路径

```text
今日收银
  → 团购数据
  → 核销明细
  → 收入明细
```

该路径只处理团购券，不增加外卖入口。

### 14.2 今日收银当前接口口径

`merchantToday(date)` 按北京时间自然日汇总：

- 成功核销笔数；
- 商品售价；
- 商家补贴；
- 平台补贴；
- 顾客实付；
- 服务费；
- 商家预计收入；
- 成功退款数和退款金额。

当前代码的展示计算为：

```text
核销金额 redemptionAmount = customerPaidAmount + platformSubsidyAmount
净收金额 netReceiptAmount = estimatedIncomeAmount - refundAmount
```

这是当前接口展示口径。对于已核销退款的严谨财务对账，应查看 `REFUND_REVENUE_REVERSED` 和 `SERVICE_FEE_REFUNDED`，不能只用“预计收入减消费者退款金额”替代账本净额。

### 14.3 团购数据

按商品聚合时应全部来源于核销快照，典型字段包括：

- 商品名称和当时售价；
- 核销数量与核销金额；
- 商家补贴、平台补贴；
- 服务费；
- 退款数量和退款金额；
- 商家预计收入。

### 14.4 核销明细

一条核销明细至少能追溯：

- 核销时间和核销码摘要；
- 商品、订单、用户券和核销记录；
- 顾客实付、两类补贴、服务费、预计收入；
- 核销状态和退款状态；
- 是否进入结算批次。

### 14.5 收入明细

业务展示可理解为：

```text
收入净额 = 顾客实付 + 平台补贴 - 服务费 - 已发生的收入冲回 + 服务费返还
```

最终对账必须按账本分录求和。每条收入记录应可追溯到：

- 订单；
- 订单明细；
- 用户券；
- 核销记录；
- 退款及逐券退款明细；
- 账本事件；
- 结算批次。

### 14.6 三层一致性检查

```text
第一层：核销快照
顾客实付 + 平台补贴 - 服务费 = 商家预计收入

第二层：账本
核销确认 + 服务费扣减 + 各类冲回/返还 = 可结算净额

第三层：结算
settlement_item 对应分录之和 = settlement_batch.total_amount
```

## 15. 平台客服业务模型

### 15.1 服务拓扑

```text
消费者 → 平台客服
商户   → 平台客服
```

当前不是“消费者直接联系商户客服”。商户不能查看消费者创建的工单，也不能查看消费者与平台客服之间的会话。

### 15.2 工单类型和优先级

类型：

```text
REFUND
REDEMPTION
ORDER
SETTLEMENT
GENERAL
```

优先级：

```text
LOW
NORMAL
HIGH
URGENT
```

新工单默认 `NORMAL`，默认 SLA 截止时间为创建后 4 小时。

### 15.3 权限真源

外部申请人的可见性只由以下组合决定：

```text
applicant_type + applicant_id
```

消费者：

```text
applicant_type = CONSUMER
and applicant_id = 当前消费者 ID
```

商户：

```text
applicant_type = MERCHANT
and applicant_id = 当前商户账号 ID
```

`related_user_id`、`related_shop_id`、`shop_id`、`order_id`、`voucher_id`、`refund_id` 和 `redemption_id` 只是业务上下文，不能扩大查询权限。尤其不能只按 `shop_id` 查询全部工单，否则商户可能看到消费者工单。

### 15.4 关联业务校验

创建工单时服务端会校验：

- 订单、券、退款、核销记录是否存在；
- 是否属于当前消费者或商户账号可访问范围；
- 多个关联资源是否属于同一订单链路；
- 商户相关资源是否属于当前门店。

不存在和越权统一返回“关联业务不存在或不属于当前账号”，避免用错误差异探测他人数据。

## 16. 客服状态机

### 16.1 白名单

```text
OPEN
  → CLAIMED
  → CLOSED

CLAIMED
  → WAITING_CUSTOMER
  → WAITING_MERCHANT
  → WAITING_INTERNAL
  → RESOLVED

WAITING_CUSTOMER
  → CLAIMED
  → CLOSED

WAITING_MERCHANT
  → CLAIMED
  → CLOSED

WAITING_INTERNAL
  → CLAIMED
  → CLOSED

RESOLVED
  → CLAIMED
  → CLOSED

CLOSED
  → 无普通状态转换
```

所有人工状态更新都在服务层校验白名单，前端不能任意写最终状态。

### 16.2 原子认领

认领使用带条件的单条更新：

```sql
UPDATE customer_service_ticket
SET assignee_admin_id = ?, status = 'CLAIMED', version = version + 1
WHERE id = ?
  AND assignee_admin_id IS NULL
  AND status = 'OPEN';
```

两个客服同时认领时，只有影响行数为 1 的请求成功，另一个收到“已被认领或状态不可认领”冲突。

### 16.3 公开回复

- 客服公开回复消费者工单后进入 `WAITING_CUSTOMER`；
- 客服公开回复商户工单后进入 `WAITING_MERCHANT`；
- 首次公开回复记录 `first_response_time`；
- 每次公开回复更新 `last_response_time` 和等待开始时间；
- 申请人回复相应等待状态时，工单唤醒到 `CLAIMED`；
- 唤醒要求工单已经有处理人，未认领工单不能伪造为处理中。

### 16.4 内部备注

- 可见性为 `INTERNAL`；
- 只允许管理端查看；
- 更新 `has_internal_note`；
- 不改变工单主状态；
- 消费者和商户的消息列表、未读统计和附件访问均排除内部备注。

### 16.5 解决、关闭和重开

- `RESOLVED` 表示业务已解决，但消费者仍可重新打开；
- `CLOSED` 后普通消息和状态接口不能继续修改；
- 消费者可直接重开 `RESOLVED`；
- `CLOSED` 仅在 `reopen_deadline` 内可重开；
- 关闭时重开期限设置为 7 天；
- 重开后有原处理人则回到 `CLAIMED`，没有处理人则回到 `OPEN`；
- 重开后 SLA 重新设置为 4 小时。

当前消费者端提供关闭和重开接口；商户端当前提供创建、列表、详情、回复和消息查询，尚未提供与消费者完全对称的关闭/重开接口。

### 16.6 自动关闭

- 默认每小时扫描一次；
- `RESOLVED`、`WAITING_CUSTOMER`、`WAITING_MERCHANT` 连续空闲 7 天可自动关闭；
- 依据最后消息时间或更新时间判断空闲；
- 自动关闭仍使用状态条件更新，避免覆盖并发的新状态；
- 关闭后设置 7 天重开期限。

## 17. 客服转交、标签和快捷回复

### 17.1 转交

- 目标必须是启用的 `CUSTOMER_SERVICE` 或 `PLATFORM_ADMIN`；
- 普通客服只能操作本人负责的工单，平台超级管理员可治理其他客服工单；
- `RESOLVED/CLOSED` 不能转交；
- 转交后状态归一为 `CLAIMED`；
- 清理等待消费者/商户时间；
- 追加原客服、新客服、操作人、原因和时间；
- 转交记录只追加，不覆盖历史。

### 17.2 标签

- 标签来自启用的标签字典；
- 替换时拒绝重复标签和停用标签；
- 工单和标签通过关系表维护；
- 队列可以按标签筛选；
- 退款、核销、结算和高优先级可以用标签辅助运营，但标签不能改变退款或结算状态。

### 17.3 快捷回复

```text
PERSONAL  个人模板
TEAM      团队模板
```

- 普通客服可创建和删除自己的个人模板；
- 平台超级管理员维护团队模板；
- 删除采用停用，不抹除历史使用事实；
- 快捷回复只是填充消息内容，不绕过回复权限和工单状态校验。

## 18. 消息、未读和附件

### 18.1 消息类型与可见性

消息类型：

```text
TEXT
IMAGE
ATTACHMENT
SYSTEM
```

可见性：

```text
PUBLIC    申请人和管理端可见
INTERNAL  仅管理端可见
```

### 18.2 游标分页

```text
before_message_id  加载更早历史
after_message_id   拉取更新消息
limit              1..100，默认 30
```

`before_message_id` 和 `after_message_id` 不能同时提交。消息按 ID 游标读取，避免页码分页在会话新增消息时发生重复或遗漏。

### 18.3 已读游标和未读

已读位置按以下组合唯一：

```text
ticket_id + reader_type + reader_id
```

数据库使用 `GREATEST(旧游标, 新游标)` 幂等推进，因此并发或乱序请求不能让游标倒退。未读统计：

- 排除阅读者本人发送的消息；
- 消费者和商户只统计公开消息；
- 管理端可统计公开消息、内部备注和系统事件；
- 打开列表不等于全部已读，读取消息后才推进对应游标。

### 18.4 附件生命周期

```text
TEMPORARY  已上传、尚未绑定消息
BOUND      已绑定工单消息
DELETED    已删除
```

- 当前只接受 JPEG、PNG、WebP 图片；
- 临时附件有效期 24 小时；
- 绑定时再次校验工单、上传者、登录域和过期时间；
- Local/S3 存储对象均按私有文件处理；
- 每次读取重新校验工单归属和消息可见性；
- 跨工单附件、他人的临时附件、外部读取内部备注附件统一按不存在处理；
- HTTP 响应使用 `no-store`，避免私有附件被共享缓存。

## 19. SLA 与客服队列

### 19.1 当前 SLA

- 新建和重开工单默认 SLA 为 4 小时；
- 每 60 秒刷新一次超时标记；
- `RESOLVED/CLOSED` 不计为超时；

## 20. 客服与退款的边界

客服可在权限校验后查看工单关联的：

- 订单；
- 用户券；
- 核销记录；
- 退款申请和逐券明细；
- 审核记录；
- Mock 执行状态；
- 退款时间线；
- 相关结算上下文。

客服权限：

```text
admin:customer-service:read    查看队列、详情和消息
admin:customer-service:manage  认领、回复、备注、状态、转交、标签、快捷回复
```

退款敏感操作要求独立权限：

```text
admin:refund:manage
```

因此，客服不能通过工单状态、内部备注或标签直接完成退款审批。正确做法是跳转退款工作台，在退款权限和退款状态机内审批或重试，再由工单显示最新退款事实。

## 23. 典型案例

### 23.1 未核销单券自动退款

条件：订单实付 90 元，单张券未核销，商品允许随时退。

```text
消费者申请
→ 校验通过
→ AUTO_APPROVED
→ WAITING_EXECUTION
→ Worker 领取为 PROCESSING
→ Mock SUCCESS
→ 券 REFUNDED
→ 消费者退款 90 元
→ 写 REFUND_REVERSED -90 元
→ 不冲回核销收入，不返还服务费
```

### 23.2 已核销券人工退款

沿用第 5.5 节示例：顾客实付 90 元、平台补贴 5 元、服务费 4.50 元。

```text
商户或管理员发起
→ PENDING_REVIEW / UNDER_REVIEW
→ 管理员人工通过
→ Mock 退款成功
→ REFUND_REVERSED          -90.00 元
→ REFUND_REVENUE_REVERSED  -95.00 元
→ SERVICE_FEE_REFUNDED      +4.50 元
```

退款后对商家结算净影响为 `-90.50 元`，正好冲回原商家预计收入 `95.00 - 4.50 = 90.50 元`。

### 23.3 三券订单部分退款

订单实付 `100.00 元`，三张券分摊 `33.33、33.33、33.34 元`，只退款最后一张：

```text
实际退给消费者 33.34 元
最后一张券 → REFUNDED
前两张券状态不变
支付状态 → PARTIALLY_REFUNDED
售后状态 → PARTIALLY_REFUNDED
后续退款只能选择尚未退款的券
```

### 23.4 已结算后退款

```text
D1 核销并写收入/服务费分录
→ D2 02:00 进入结算批次并成功
→ D3 人工批准已核销退款
→ D3 写收入冲回和服务费返还
→ D4 02:00 两条新分录进入下一批次
→ D2 历史成功批次不修改
```

### 23.5 客服协助但不越权退款

```text
消费者创建 REFUND 工单并关联退款 ID
→ 工单 OPEN
→ 客服 A 原子认领为 CLAIMED
→ 客服查看退款处于 PENDING_REVIEW
→ 客服添加内部备注，不改变工单状态
→ 有退款权限的管理员在退款工作台审批
→ Worker 执行成功
→ 客服刷新退款上下文后公开回复消费者
→ 工单 WAITING_CUSTOMER
→ 问题确认解决后 RESOLVED/CLOSED
```

## 24. 对账公式与排查顺序

### 24.1 单次核销守恒

```text
顾客实付 + 平台补贴 = 商家毛应收
商家毛应收 - 服务费 = 商家预计收入
```

### 24.2 已核销退款守恒

```text
原商家预计收入
= 顾客实付 + 平台补贴 - 服务费

退款对商家结算净影响
= -(顾客实付 + 平台补贴) + 服务费
= -原商家预计收入
```

### 24.3 排查顺序

发现页面金额不一致时按以下顺序排查：

1. 查订单和用户券的逐券支付分摊，确认余数位置；
2. 查 `voucher_redemption` 快照，禁止先看商品当前价格；
3. 用快照重算服务费基数、服务费和预计收入；
4. 查同一 `business_event_id` 的账本分录及唯一性；
5. 查 `voucher_refund_item` 的可退额、实退额、核销标记和冲回金额；
6. 查退款执行尝试、租约、重试次数和渠道流水；
7. 查账本是否已绑定 `settlement_item`；
8. 汇总批次明细并与 `settlement_batch.total_amount` 比较；
9. 最后再检查前端单位转换、符号和日期时区。

### 24.4 常见误区

- 用商品当前价格重算历史核销；
- 把平台补贴当成消费者退款金额；
- 未核销退款也返还服务费；
- 已核销退款只退消费者，不冲回商家收入；
- 把 `REFUND_REVERSED` 直接纳入商家结算；
- 修改已成功结算批次来表达后续退款；
- 把订单 `PAID` 误认为没有售后；
- 把 WebSocket 连接误认为 Worker 正在退款；
- 客服通过修改工单状态替代退款审批。

## 25. 幂等、并发与一致性

### 25.1 幂等键

- 消费者、商户和管理员创建退款均要求 `Idempotency-Key`；
- 管理端退款审批、拒绝和重试要求幂等键；
- 结算重试要求幂等键；
- 自动过期退款使用稳定的券级幂等键；
- 渠道执行使用稳定幂等键，支持失败恢复重放。

HTTP 幂等窗口不能替代数据库唯一约束、行锁和状态条件更新。

### 25.2 并发控制

- 退款申请锁定业务事实并检查同券活动退款；
- 退款审核通过退款主记录行锁串行化；
- 执行任务用状态和租约条件原子领取；
- 结果提交锁执行尝试并校验租约所有者；
- 客服认领使用单条条件更新；
- 客服状态和转交锁定工单；
- 已读游标使用 `GREATEST` 防止倒退；
- 账本用业务事件唯一约束防止重复入账；
- 结算批次用门店和结算日唯一约束防止重复生成。

### 25.3 事务边界

- 退款申请：申请主表、逐券明细、锁券和售后聚合在同一业务事务中；
- 退款执行：领取短事务、事务外渠道调用、结果短事务相互分离；
- 退款成功：券、退款、支付、售后和账本在结果事务中一致落地；
- 客服操作：工单、消息、标签或转交与审计按各自业务事务处理；
- 结算：当前批次、明细、尝试和同步 Mock 仍在现有结算事务模型中处理。

- `ALWAYS_FAIL` 进入人工处理；
- `DELAYED` 先处理中后成功；
- 未核销退款不产生商家收入冲回和服务费返还；
- 已核销退款完整产生三类退款分录；
- 同一业务事件不会重复入账；
- `UNUSED/EXPIRED` 自动过期退款都覆盖。

### 27.3 客服

- 消费者不能访问他人工单；
- 商户不能访问其他商户或消费者工单；
- 关联资源不存在和越权响应一致；
- 两客服并发认领仅一个成功；
- 非法状态转换被拒绝；
- 内部备注不改变主状态且外部不可见；
- 公开回复正确进入等待申请人状态；
- 申请人回复正确唤醒到 `CLAIMED`；
- 转交后处理权限正确；
- 消息游标无重复、无遗漏；
- 已读游标不会倒退；
- 附件不能跨工单、跨登录域读取；
- 已关闭工单不能继续修改；
- 7 天自动关闭和 7 天重开期限正确；
- SLA 超时排序正确。

### 27.4 契约与实时连接

- OpenAPI 业务 ID 均为字符串；
- `operationId` 唯一；
- 权限错误、参数错误和状态冲突响应完整；
- WebSocket 断开和重连不修改退款、客服或结算状态；
- 应用重启后退款队列可从数据库租约恢复。

## 28. 接入真实渠道时的替换点

### 28.1 退款

保持 `RefundGateway` 端口不变，增加真实适配器：

- 请求签名和证书管理；
- 商户退款单号与渠道退款单号；
- 渠道幂等键；
- 明确的成功、失败、处理中映射；
- 主动查询和异步回调双通道；
- 回调验签、防重放和原始报文审计；
- 渠道成功、本地失败的恢复任务；
- 日终渠道退款对账。

业务层仍以本地退款主表、逐券明细、执行尝试和账本为权威，不把渠道回调直接当成页面状态来源。

### 28.2 结算

建议在现有 `settlement_attempt` 上补齐：

```text
Coordinator
→ LeaseService 原子领取
→ SettlementGateway 事务外调用
→ ResultService 独立事务提交
→ 查询/回调恢复
→ 渠道日终对账
```

同时定义负批次、打款退票、账户冻结、人工复核、轧差、追缴和会计科目映射。

### 28.3 客服

若以后接 Chatwoot、Zammad 或其他全渠道系统，应把它们作为外部适配器，而不是替换本地业务权限真源。至少保持：

- 本地工单与外部会话 ID 映射；
- 消费者/商户身份隔离；
- 内部备注可见性；
- 附件私有访问；
- 退款审批权限仍由 Roamly 管理；
- 回调幂等、乱序处理和审计。
