# Roamly 地域隔离、推荐算法与测试数据说明

> 文档状态：已实现（开发种子与后端规则）  
> 更新时间：2026-09-13
> 适用范围：消费者首页推荐动态、店铺发现、门店列表与定位上下文

## 1. 设计目标

Roamly 将“能看哪些数据”和“同城内容如何排序”拆成两层：

```text
城市：硬隔离，决定候选数据范围
区县：软加权，只影响推荐顺序，不排除同城其他区县
距离：真实定位下的连续排序因素
```

这样可以保证用户切换到西宁后不会看到杭州内容，同时不会因为区县边界把同城门店、商品或动态完全隐藏。

本期不引入向量数据库、不做语义召回，也不新增城市表或区县业务表。

## 2. 定位上下文

### 2.1 三种模式

| 模式 | 城市来源 | 区县 | 经纬度 | 用途 |
|---|---|---|---|---|
| `REAL_LOCATION` | 服务端根据微信坐标解析 | 有 | 有 | 区县加权、距离衰减、距离排序 |
| `MANUAL_CITY` | 用户手动选择 | 无 | 无 | 按选中城市浏览 |
| `DEFAULT_CITY` | 默认杭州 `330100` | 无 | 无 | 未授权或定位失败时继续浏览 |

手动城市和默认城市不能携带旧的区县或经纬度。客户端不提交 `districtCode`，区县只由后端从真实坐标解析得到。

### 2.2 服务端解析规则

`POST /v1/location/context` 使用微信 `gcj02` 坐标，与数据库中启用区县的中心点和服务半径进行匹配，返回独立的：

- `cityCode` / `cityName`
- `districtCode` / `districtName`
- 原始坐标和定位精度（仅作为当前请求上下文，不写入动态推荐数据）

店铺发现和推荐动态接口在收到完整经纬度时，服务端会覆盖客户端传入的 `cityCode`，避免伪造城市或区县。

## 3. 数据隔离规则

### 3.1 城市硬隔离

以下公开查询都必须使用生效城市：

- 首页推荐动态
- 店铺发现和店铺与店内可售券关键词搜索
- 门店列表和门店关键词搜索
- 门店点评（通过所属门店继承城市）

SQL 层使用 `city_code = ?` 作为候选集条件。未提供真实坐标时，客户端选择的城市是兼容入口；提供完整坐标时，以服务端解析城市为准。

### 3.2 区县软加权

区县只用于以下推荐排序：

- 首页“推荐”动态流
- 店铺默认“综合推荐”排序

区县不会出现在城市候选集的 `WHERE` 硬过滤条件中，因此同城其他区县和 `district_code IS NULL` 的数据仍可返回。

关注流、分区流、门店点评和显式排序不叠加区县推荐权重。

### 3.3 距离规则

- 只有 `REAL_LOCATION` 模式有真实距离。
- 店铺综合推荐使用距离衰减；门店 `DISTANCE` 使用纯距离排序。
- 手动城市或默认杭州点击“距离”时，前端应提示恢复定位，不伪造坐标。
- 缺少经度或纬度时，距离排序返回 `DISTANCE_REQUIRES_COORDINATES`；坐标只提交一半返回 `INCOMPLETE_COORDINATES`。

## 4. 推荐算法

### 4.1 动态推荐流

动态基础热度分：

```text
base_score = liked_count × 1000
           + comment_count × 2000
           + floor(create_time 的 Unix 时间戳 / 3600)
```

真实定位且解析到当前区县时：

```text
rank_score = base_score × 120    当前区县
rank_score = base_score × 100    同城其他区县或区县为空
```

数据库使用整数缩放后的 `rank_score` 排序，游标条件和下一页偏移使用同一表达式，避免翻页重复或漏数据。无真实定位时所有同城动态使用 `×100` 的城市级分值。

### 4.2 分类独立的店铺推荐

`GET /v1/shops/discovery` 要求 `categoryId=1`（美食）或 `2`（休闲娱乐），可选 `typeId` 只能为该一级分类的子类。先以城市、分类、营业状态及关键词限定店铺候选，再排序和分页；不跨分类补位。总数按店铺计数。

```text
sold = SUM(店铺全部券的 sold_count)，沿用累计支付销量语义，不表示消费人数
smooth_score = (shop.score / 10 × shop.comments + 3.5 × 10) / (shop.comments + 10)
base = 100 + 100 × ln(1 + sold) + 20 × smooth_score
recommended_score = base × district_factor × distance_factor
district_factor = 1.15（真实定位同区县）；否则 1
distance_factor = 1 / (1 + distance_meters / 3000)；无真实定位为 1
```

评分展示使用真实点评分，无点评显示“暂无评分”。新店仍有基础分。没有全站归一化、跨分类权重、行为个性化或模型训练。

排序支持 `RECOMMENDED / DISTANCE / SALES / SCORE`，后三项不叠加推荐因子；最终均以店铺 ID 升序稳定排列。没有坐标的距离排序返回 `DISTANCE_REQUIRES_COORDINATES`。

店铺页查询、总数、券候选在同一个只读事务中完成。券查询只读取本页店铺，使用窗口函数读取每店热销前两条与低价前两条（合计最多四条），再选出热销一张和其余中的最低价一张。关键词匹配优先，两张不重复。计数使用窗口函数保留完整可售券数量，无券店铺仍返回。

公开可售条件：营业门店、APPROVED、ON_SALE、库存大于零、当前时刻在销售时间内。详情和交易共用 `VoucherAvailability`；SQL 和原子扣库存保持同样约束。

原 `GET /v1/voucher-products` 全站商品流已下线；店内券、券详情、媒体和下单路径保留。

## 5. 开发种子测试数据

### 5.1 城市约束

开发种子只保留两个城市，不新增城市：

| 城市 | 编码 |
|---|---|

| 西宁 | `630100` |

### 5.2 区县

在两个既有城市下补充区县，用于验证同城跨区县推荐：

| 城市 | 区县 | 编码 | 定位用途 |
|---|---|---|---|
| 杭州 | 拱墅区 | `330105` | 原有默认杭州定位样例 |
| 杭州 | 西湖区 | `330106` | 同城其他区县商品和动态 |
| 杭州 | 上城区 | `330102` | 同城第二对照区县 |
| 西宁 | 城北区 | `630105` | 青海师范大学城北校区定位样例 |
| 西宁 | 城东区 | `630102` | 同城其他区县商品和动态 |
| 西宁 | 城中区 | `630103` | 同城第二对照区县 |

### 5.3 门店与商品

新增门店和商品均使用既有城市，不创建新城市：

| 门店 | 城市/区县 | 商品样例 | 测试重点 |
|---|---|---|---|
| 西湖边的慢时光（ID 5） | 杭州/西湖区 | 3201、3202 | 当前区县加权与高销量对比 |
| 城东夜食集（ID 6） | 西宁/城东区 | 3203、3204 | 西宁同城跨区县与距离衰减 |
| 城北校园漫游咖啡（ID 4） | 西宁/城北区 | 3205 | 当前定位区县商品 |
| 漫游咖啡实验室（ID 2） | 杭州/拱墅区 | 3206 | 杭州同城对照商品 |

新增商品均为 `APPROVED + ON_SALE`，销量、评分、价格和坐标刻意设置为不同值，便于观察“区县权重不会绝对压过销量/评分”和“距离越近通常越优”的效果。

### 5.4 动态

动态样例覆盖：

- 杭州拱墅区、西湖区、上城区和区县为空
- 西宁城北区、城东区、城中区和区县为空
- 同城不同区县的不同点赞数

动态 ID `1101`～`1108` 是新增推荐对照数据；区县为空的动态不会获得区县加权，但仍参与城市推荐。

## 6. 建议验收场景

### 场景 A：西宁城北区真实定位

请求推荐动态时提交西宁城北区附近的完整坐标：

```text
GET /v1/feeds/recommended?cityCode=330100&longitude=101.749746&latitude=36.742782
```

预期：

1. 服务端忽略伪造的杭州 `cityCode`，使用西宁 `630100`。
2. 城北区动态优先，但城东区、城中区和区县为空的西宁动态仍可出现。
3. 杭州动态不可见。

### 场景 B：手动城市与分类隔离

`GET /v1/shops/discovery?cityCode=630100&categoryId=1&sort=RECOMMENDED` 只返回西宁美食店铺，无区县与距离加成。切换 `categoryId=2` 只返回休闲娱乐；传入美食二级分类应返回 400。

### 场景 C：真实定位、显式排序和选券

传入城北区真实坐标，以同店不同券验证热销＋低价、关键词优先、无重复及可售限制；改用 DISTANCE 后只按距离排序。手动城市点击距离时提示恢复定位。

### 场景 D：页状态和数据变动

两个分类保存独立搜索、筛选、页码、列表和滚动位置，城市与坐标变化使旧状态失效。固定数据分页不重不漏；销量等动态变化后刷新排序，前端按店铺 ID 去重。修改美食店铺销量不改变休闲娱乐排序。

## 7. 数据重建与注意事项

`seed-dev.sql` 是可重建的开发种子，不是生产迁移脚本。数据库级验收会重建 `schema-init.sql` 与 `seed-dev.sql`，测试结束后恢复纯种子状态。

不要在生产环境执行该文件，也不要把开发账号、测试商品或测试门店复制到生产数据。

### 7.1 海量推荐测试数据

开发种子默认额外生成 2,000 个消费者、300 家门店、3,000 个商品、20,000 条动态、100,000 个动态点赞、30,000 条评论和 10,000 条门店点评。数据只使用杭州 `330100` 与西宁 `630100`，每个城市扩展 9 个区县；动态、商品和门店通过确定性取模均匀分布，能够稳定复现同城硬隔离、区县软加权、销量/评分排序和游标翻页场景。订单、用户券、核销、退款和客服数据与这些主体记录保持逻辑关联，避免推荐页面只有孤立内容。

批量生成区使用临时数字表，不改变城市表，不依赖自增 ID。详细区间、重建步骤和一致性校验见[数据库表结构与开发数据说明](数据库表结构与开发数据说明.md#海量开发数据规范)。

## 8. 参考来源

以下资料用于支撑定位能力和地理排序实现，产品层“城市浏览/当前定位分离”是对主流本地生活产品公开行为的抽象，不代表其内部实现：

1. 微信小程序 `wx.getLocation`（授权、拒绝和 `gcj02` 坐标）：  
   <https://developers.weixin.qq.com/miniprogram/dev/api/location/wx.getLocation.html>
2. MySQL `ST_Distance_Sphere`（球面距离计算，单位米）：  
   <https://dev.mysql.com/doc/refman/8.0/en/spatial-convenience-functions.html>
3. Redis `GEOSEARCH`（大规模附近检索的可选方案；本项目当前未使用）：  
   <https://redis.io/docs/latest/commands/geosearch/>
4. Elasticsearch `function_score`（将地理或业务特征作为排序函数的通用方案；本项目当前使用 SQL 规则排序）：  
   <https://www.elastic.co/guide/en/elasticsearch/reference/current/query-dsl-function-score-query.html>

本项目当前选择 MySQL 关系字段和 `ST_Distance_Sphere`，原因是城市/区县属于硬业务字段，现阶段数据量适合规则排序；向量数据库不适合承担城市隔离或区县权重职责。
