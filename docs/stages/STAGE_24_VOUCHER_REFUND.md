## 目标

实现消费者未核销单券退款、财务异常退款和订单支付状态聚合；不接入真实微信退款。

## 设计复核（v2）

- 每张用户券单独建立退款单，金额由订单实付按序号整数分摊；同一券同一幂等键只产生一笔退款。
- Mock 退款申请先落 `REQUESTED`（已申请），由管理端审批或重试推进到 `PROCESSING`（处理中）和 `SUCCEEDED`（退款成功）；异常路径可落 `FAILED`（退款失败）并允许原单重试。
- 退款只改变券状态和订单聚合状态，不返还库存、不回退销量；跨用户访问统一返回 404。
- 管理端审批与重试复用固定角色权限，所有命令要求 `Idempotency-Key` 并写入操作审计。

## 进入条件与涉及端

- 进入条件为阶段 23 已实现，支付交易、逐份券、金额分摊和订单聚合事实已经通过幂等与竞态验收。
- 涉及后端、消费者小程序和管理 Web；商户端只在后续订单只读展示中观察退款结果。

## 状态机、数据与权限

- 退款使用 `REQUESTED`（已申请）、`PROCESSING`（处理中）、`SUCCEEDED`（退款成功）、`FAILED`（退款失败）、`REJECTED`（退款被拒），订单和券状态由退款结果聚合更新。
- 新增 `voucher_refund`，退款金额引用单券支付分摊事实；字段、唯一约束和聚合规则以数据库契约为准。
- 消费者只能申请自己的可退券；`PLATFORM_ADMIN`（平台超级管理员）与 `FINANCE`（财务管理员）处理异常退款，其他角色只可按权限查看。

## 后端

- 新增 `voucher_refund`，退款号唯一；消费者按券申请，不能模糊退整单。
- 随时退仅允许未使用有效券，过期退仅允许完全未使用的过期券；次卡首次使用后禁止自助退款。
- 状态为 `REQUESTED`（已申请）、`PROCESSING`（处理中）、`SUCCEEDED`（退款成功）、`FAILED`（退款失败）、`REJECTED`（退款被拒）。
- Mock 退款审批幂等更新券和订单聚合支付状态；不返库存，不回退支付销量；消费者退款说明最多 100 字且单券数量固定为 1。
- 退款响应同时返回固定 `reasonCode` 与消费者可读的 `reason` 文案，退款单号、商家单号和原支付渠道由服务端事实生成。
- 财务异常退款必须填写原因与金额，不能超过券尚未退款余额，并写事务感知审计。

## 接口

- 消费者 `POST /v1/users/me/vouchers/{voucherId}/refunds`，要求 `Idempotency-Key`。
- 管理端 `GET /v1/admin/refunds`、`GET /v1/admin/refunds/{id}`。
- 管理端 `POST .../{id}/approval`、`/rejection`、`/retry`，按权限和状态开放并要求幂等键。

## 客户端

- 消费者券详情展示退款资格、规则、确认和结果；不满足条件时隐藏按钮并展示原因。
- 管理 Web 提供退款列表、详情、金额、历史处理、通过、驳回和失败重试。
- 409 时两端刷新服务端状态，不重复创建申请。

## 失败处理

- 重复申请、并发处理、金额越界或券状态变化返回幂等事实或 409，不产生第二笔退款。
- Mock 网关失败保留可重试状态和原因；审计失败、券更新失败或聚合失败必须按事务边界回滚。
- 无权限返回 403，跨用户券返回 404，已核销或不满足规则返回稳定业务错误码。

## 验收

- 退款资格、金额上限、重复申请、并发处理、部分/全部退款聚合和越权测试通过。
- 消费者与管理 Web 自动化覆盖成功、拒绝、失败、重试和冲突。
- Mock 退款真实 HTTP、数据库和审计结果通过后标记“已实现”。
