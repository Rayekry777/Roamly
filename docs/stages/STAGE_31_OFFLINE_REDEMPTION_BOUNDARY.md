# Stage 31：核销与线下收款解耦

## 目标与边界

本阶段将核销限定为团购券履约事实：校验券码、门店、权限、有效期和剩余次数，原子扣减次数并记录审计。顾客到店后超出券面权益的消费由顾客与商户自行使用微信支付；平台不采集、不计算、不生成支付单、不写账本，也不参与该笔线下结算。

团购券购买支付、退款、发券和平台佣金结算继续保留。平台收入只来自团购券订单的线上实付金额。

## 接口契约

- `VoucherRedemptionPreviewDTO` 仅包含 12 位 `code`。
- `VoucherRedemptionPreviewVO` 返回券型、券面权益、有效期、使用规则、剩余次数和 `expiresAt`，不返回消费金额。
- `VoucherRedemptionVO` 只返回核销 ID、券/门店、操作人、使用次数、剩余次数、状态及核销/撤销时间。
- 预览令牌只保存 voucher、shop、操作账号和过期时间；确认仍使用预览令牌与 `Idempotency-Key`。

## 财务事实

支付成功写入 `PAYMENT_FROZEN`。核销成功根据 `user_voucher.order_id` 对应订单的 `pay_amount`、购买数量和券的总使用次数做确定性整数分摊：除不尽的余数归最后一张券、最后一次核销。佣金先按订单实付金额计算，再按同一规则分摊，保证收入和佣金守恒。

撤销核销恢复使用次数，并追加 `REDEMPTION_REVERSED` 与 `COMMISSION_REVERSED` 负向事实；已进入结算明细的核销禁止撤销。任何退款或撤销在已结算日之后产生的负向账本分录，进入后续结算日的调整批次。

每天 02:00 按门店和结算日扫描前一日的可结算账本，生成 `settlement_batch` 与 `settlement_item`。门店和结算日唯一约束保证重复执行返回同一批次；明细金额按商户净结算口径签名：佣金确认是负项，佣金冲回是正项，核销撤销是负项。重试只更新原失败批次，不创建新批次。

## 客户端边界

商户端不再输入或提交消费金额，预览和核销记录只展示券面规则、使用次数和有效期；成功提示顾客与商户自行线下微信支付额外消费。管理端核销审计和导出删除消费金额、抵扣金额，但财务页继续展示线上订单收入、佣金和结算。消费者端保留购买订单金额和券面权益，并统一提示额外消费线下结算。

## 数据库与验收

`voucher_redemption` 不保存线下金额字段；`voucher_product` 的面值和最低消费作为代金券规则展示，核销券不参与消费金额计算。Demo 数据库直接重建，不对需要保留数据的数据库执行 `schema-init.sql`。

验收至少覆盖：四类券直接预览和核销、跨店/过期/重复拒绝、次卡多次分摊、订单实付金额和佣金守恒、撤销负向账本、已结算禁止撤销、T+1 批次幂等、退款后续负向调整、三端页面和 OpenAPI Schema 不再出现核销金额字段。
